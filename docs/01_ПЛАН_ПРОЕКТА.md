## 0. ЧТО УЖЕ ИЗВЕСТНО ОБ ЭТОМ ОКРУЖЕНИИ (и меняет часть плана)

Этот раздел — не теория, а результаты экспериментов, проведённых в этом же окружении.
Три факта напрямую затрагивают вашу архитектурную договорённость.

### 0.1. CODESYS допускает в `<body>` РОВНО ОДИН элемент `<FBD>`

Проверено импортом: «недопустимый дочерний элемент FBD; ожидается addData, documentation».
**Следствие:** POU — это **одна сеть**, а не список сетей. «Цепочка из N экземпляров
`FB_CPU_Core` на главном листе» и «порядок исполнения: fetch → decode → …» как **отдельные
сети** в одном POU невыразимы. Это надо решать архитектурно (см. §4).

### 0.2. Вызов экземпляра FB через PLCopen XML — ПОДТВЕРЖДЁН ✅

**Шаг 0 выполнен, вопрос закрыт.** Проверены три варианта записи вызова; CODESYS
вернул схему обратно **дословно** в виде:

```xml
<block localId="10000000002" typeName="CALLEE" instanceName="Inst">
```

при объявлении экземпляра в `VAR`: `Inst: CALLEE;`. Это **каноническая форма самого
CODESYS** — то есть запись распознана как настоящий вызов функционального блока.

**Рабочий рецепт:**
```xml
<!-- в <interface><localVars> -->
<variable name="Core0"><type><derived name="FB_CPU_Core" /></type></variable>

<!-- в <FBD> -->
<block localId="N" typeName="FB_CPU_Core" instanceName="Core0" executionOrderId="k">
  <position x="..." y="..." />
  <inputVariables> <variable formalParameter="Enable"> ... </variable> </inputVariables>
  <inOutVariables />
  <outputVariables> <variable formalParameter="Done" /> </outputVariables>
</block>
```

**Следствие:** «N последовательно включённых экземпляров `FB_CPU_Core`, активные
включаются мультиплексором по счётчику» реализуется **буквально**, как в вашей
договорённости. Вариант B из §4 (встраивание копий) остаётся резервом, но не нужен.

### 0.3. CODESYS молча отвергает часть схем по содержимому

Экспериментально: из 16 схем 11 создаются, 4 не создаются молча (без исключения,
детерминированно, на чистых сессиях при обоих вариантах настройки), 1 роняет процесс.
Опровергнуто как причина: размер файла, тип блока, порядок импорта, асинхронность,
ссылки вперёд, дубли `localId`, состояние сессии.
**Следствие:** нельзя «нарисовать всё и залить». Нужен цикл «сгенерировал → импортировал →
проверил состав → бисекция упрямой схемы», инструменты для него уже написаны (§7).

## 1. АРХИТЕКТУРНАЯ СХЕМА

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ GVL_CPU   Reg_A Reg_X Reg_Y Reg_P Reg_SP : BYTE   Reg_PC : WORD              │
│ GVL_BUS   Bus_Data : BYTE   Bus_Addr : WORD   Bus_WE Bus_RE : BOOL           │
│ GVL_MEM   Mem : ARRAY[0..65535] OF BYTE                                      │
│ GVL_IO    Io_In Io_Out : BYTE  Ai0 Ao0 : WORD  IrqMask EdgeLatch Tick : BYTE │
│ GVL_SIG   все микрооперации декодера                                         │
│ GVL_DISK  Disk : ARRAY[0..2047, 0..127] OF BYTE                              │
└──────────────────────────────────────────────────────────────────────────────┘
        ▲                    ▲                        ▲
        │                    │                        │
┌───────┴────────┐  ┌────────┴─────────┐   ┌──────────┴─────────┐
│ ЯДРО 6502      │  │ ПОДСИСТЕМА CP/M  │   │ ПОДСИСТЕМА I/O     │
│                │  │                  │   │                    │
│ выборка        │  │ BIOS-подложка    │   │ FB_IOBridge        │
│ дешифратор     │  │  (FBD):          │   │  окно $F000-$F0FF  │
│ генератор адр. │  │  cold/warm boot  │   │ FB_IRQController   │
│ ALU            │  │  conin/conout    │   │  R_TRIG по DI      │
│ флаги P        │  │  disk read/write │   │ FB_AnalogBridge    │
│ стек           │  │ DiskImage        │   │  AI0/AO0 : WORD    │
│ запись/PC      │  │  образ 256 КБ    │   │ ST_PhysicalIO      │
│                │  │ (BDOS+CCP —      │   │  %IX %QX %IW %QW   │
│                │  │  готовый бинар.) │   │                    │
└────────────────┘  └──────────────────┘   └────────────────────┘
        ▲                                             ▲
        └────────── FB_TickGen / батч-счётчик ────────┘
```

**Карта памяти (фиксированная, в GVL как VAR CONSTANT):**

| Диапазон | Назначение |
|---|---|
| `$0000–$00FF` | zero page, указатели для косвенной адресации BIOS |
| `$0100–$01FF` | стек, `SP` — 8 бит, страница фиксирована |
| `$0200–$EFFF` | TPA, сюда грузятся `.COM` |
| `$F000–$F0FF` | окно memory-mapped I/O |
| `$F100–$FEFF` | свободно под расширения |
| `$FF00–$FFFF` | BIOS jump table + векторы `$FFFC/FFFD` (reset), `$FFFE/FFFF` (IRQ) |

**Карта окна I/O:**

| Адрес | Содержимое |
|---|---|
| `$F000` | дискретные входы DI (битовая карта 8 каналов) |
| `$F001` | дискретные выходы DO (чтение — состояние, запись — управление) |
| `$F002–$F003` | AI0 : WORD, little-endian |
| `$F004–$F005` | AO0 : WORD, little-endian |
| `$F006` | маска разрешения IRQ по DI |
| `$F007` | флаг фронта (edge latch), сбрасывается чтением |
| `$F008` | счётчик тактов PLC, инкремент каждый скан |

## 2. СТАНДАРТНЫЕ БЛОКИ CODESYS (все 19 проверены на импорт)

| Блок | Где применяется |
|---|---|
| `AND`/`OR`/`XOR`/`NOT` | маскирование битов, формулы флагов `V`, сборка/разбор байтов |
| `EQ`/`NE`/`LT`/`LE`/`GT`/`GE` | 100+ компараторов опкодов, `Z := (R=0)`, `LT` — перенос, сравнения в тестах |
| `SEL` | **основной блок схемы**: защёлки регистров, выбор адреса по режиму, ветвления по флагам, `CLC/SEC`, выбор активного ядра |
| `MUX` | выбор активного ядра в батче (если экземпляры окажутся доступны) |
| `ADD`/`SUB`/`MUL` | адресная арифметика, счётчики, переносы |
| `SHL`/`SHR` | сборка `PC` из LO/HI, извлечение байтов WORD |
| `BYTE_TO_WORD`/`WORD_TO_BYTE` | границы разрядности, little-endian упаковка |
| `R_TRIG` | **детектор фронта физического DI для IRQ** |
| `RS` | **edge latch в `$F007`** |
| `CTU` | счётчик тактов `$F008`, счётчик инструкций в батче |
| `TON` | опционально: «медленный такт» для наблюдения глазами |
| `SysFile` (библиотека) | чтение/запись `DISK.IMG` на SD — **единственное место со ST**, и только как файловый I/O |

## 3. КАСТОМНЫЕ FB (внутренняя логика — FBD)

| FB | Назначение | Входы | Выходы |
|---|---|---|---|
| `FB_Reg8` | защёлка байта: `Q := SEL(RESET, SEL(LOAD, Q, D), 0)` | `D:BYTE  LOAD,RESET:BOOL` | `Q:BYTE` |
| `FB_Reg16` | защёлка слова (LO/HI) | `D_LO,D_HI:BYTE  LOAD,RESET:BOOL` | `Q_LO,Q_HI:BYTE` |
| `FB_ALU_6502` | ADC/SBC/CMP. **Перенос на байтовом уровне**: `S1:=A+BX; C1:=S1<A; S2:=S1+CINX; C2:=CINX AND S2<S1; C:=C1 OR C2` | `A,B:BYTE  CIN,F_ADD,F_SUB,F_CMP:BOOL` | `R:BYTE  N,Z,C,V:BOOL` |
| `FB_Decoder6502` | 100+ `EQ` по опкодам → OR-деревья → 26 микроопераций (`LD_*`, `WR_MEM`, `ADDR_MODE`, `LEN`, `SRC`, `PC_MODE`, `SP_MODE`, `COND`, `SET_*`, `HALT`) | `Opcode:BYTE` | сигналы в `GVL_SIG` |
| `FB_Memory64K` | память + порты. **4 порта** (2 чтения + 2 записи): `JSR` пишет два байта, `RTS` читает два байта в одном скане | `RD_ADDR0/1, WR_ADDR0/1:WORD  WE0/1:BOOL  WD0/1:BYTE` | `RD0,RD1:BYTE` |
| `FB_FlagsReg` | регистр `P`, распаковка/упаковка `BYTE↔ARRAY[0..7] OF BOOL`, `bit5` всегда 1 | `P_IN:BYTE  N,Z,C,V:BOOL  SET_*:BOOL  CMD_CLC/SEC:BOOL` | `P_OUT:BYTE` + биты |
| `FB_Stack` | адреса `$0100+SP`, `$0100+SP-1`, `$0100+SP+1`, `$0100+SP+2`, новый `SP` | `SP:BYTE  SP_MODE:BYTE` | адреса, `SP_NEW`, `SP_PUSH/PULL` |
| `FB_AddrGen` | 12 режимов адресации; знаковое расширение `REL`; **баг `JMP (ind)` на границе страницы воспроизводится** | `Mode,OpLo,OpHi,X,Y:BYTE  PC,PC2:WORD` | `EFF,REL_TARGET:WORD` |
| `FB_CPU_Core` | **композитный**: один такт 6502 целиком | см. §4 | — |
| `FB_BIOS_6502` | подложка BIOS: cold/warm boot, консоль (conin/conout), чтение/запись секторов, jump table `$FF00` | `Addr:WORD  WE:BOOL  WD:BYTE` | `RD:BYTE  Vec` |
| `FB_DiskImage` | образ 256 КБ: `ARRAY[0..2047,0..127] OF BYTE`, загрузка/сохранение `DISK.IMG` | `Track,Sector:BYTE  WE:BOOL  WD:BYTE` | `RD:BYTE` |
| `FB_IOBridge` | окно `$F000–$F0FF` ↔ `ST_PhysicalIO` | `Addr:WORD  WE:BOOL  WD:BYTE` | `RD:BYTE` |
| `FB_IRQController` | `R_TRIG` по каждому DI, маска `$F006`, флаг `$F007`, линия IRQ | `Io_In:BYTE  IrqMask:BYTE  Reset:BOOL` | `Irq:BOOL  Latch:BYTE` |
| `FB_AnalogBridge` | AI0/AO0 ↔ `%IW/%QW`, `WORD` little-endian | `Ai0_Raw:WORD  Ao0_Cmd:WORD` | `Ai0_Val,Ao0_Out:WORD` |
| `FB_TickGen` | счётчик тактов `$F008`, счётчик инструкций в батче | `Enable:BOOL` | `Tick:BYTE  BatchCnt:UINT` |

**`FB_BDOS_6502` в FBD не реализуется** — по вашей договорённости BDOS+CCP берутся готовым
бинарником CP/M-65. В FBD пишется **только BIOS-подложка** (`FB_BIOS_6502`), то есть ~15
функций: `BOOT`, `WBOOT`, `CONST`, `CONIN`, `CONOUT`, `LIST`, `PUNCH`, `READER`,
`HOME`, `SELDSK`, `SETTRK`, `SETSEC`, `SETDMA`, `READ`, `WRITE`, `SECTRAN`.

## 4. ГЛАВНАЯ АРХИТЕКТУРНАЯ ПРОБЛЕМА И ЕЁ РЕШЕНИЕ

**Ваша договорённость:** «N последовательно включённых экземпляров `FB_CPU_Core`,
активные включаются мультиплексором по счётчику».

**Проблема (см. §0.1 и §0.2):** POU = одна сеть, и вызов экземпляров FB через XML не
подтверждён. Прямо «в лоб» это не собирается.

**Три варианта, по возрастанию надёжности:**

| Вариант | Как | Плюс | Минус |
|---|---|---|---|
| **A. Подтвердить синтаксис экземпляров** | пробник с 3 вариантами записи вызова (`instanceName`; `typeName`=имя экземпляра; контроль) | сохраняет вашу схему буквально | неизвестно, примет ли CODESYS |
| **B. N встроенных копий в одном листе** | `FB_CPU_Core` не экземпляр, а **функция-генератор**: генератор выдаёт N копий логики подряд в один `<FBD>`, вход каждой копии — выход предыдущей | работает гарантированно (проверено на 526 блоках) | схема N×размер; при N=32 это ~8000 блоков — тяжело, но это и есть «большая читаемая схема» |
| **C. Гибрид** | один такт на скан, а «батч» — через несколько **задач** CODESYS с разным приоритетом | просто | теряется детерминизм, который вам нужен |

**Рекомендация:** начать с **варианта A** (один пробник, дёшево). Если он зелёный —
ваша схема реализуется буквально. Если красный — **вариант B** с оговоркой: `N` берём
не 32, а **2–4** (компромисс), потому что при N=32 одна сеть становится нечитаемой
и рискует упереться в пределы импорта.

## 5. СХЕМА ТАКТА (порядок исполнения)

Один проход ядра (внутри `FB_CPU_Core` / копии):

| # | Стадия | Читает | Пишет |
|---|---|---|---|
| 0 | SNAPSHOT | `A,X,Y,P,SP,PC` | `*_F` (снимок — снимает гонки) |
| 1 | FETCH | `PC_F`, `Mem` | `Opcode`, `Op1`, `Op2` |
| 2 | DECODE | `Opcode` | `GVL_SIG.*` |
| 3 | ADDR | `ADDR_MODE`, операнды, `X_F`, `Y_F`, `PC_F` | `Bus_Addr` |
| 4 | READ | `Bus_Addr` / адреса стека | `MDR` |
| 5 | EXECUTE | `A_F/X_F/Y_F`, `MDR`, `C` | `ALU_R`, `N,Z,C,V` |
| 6 | WRITEBACK | `ALU_R`, `LD_*` | `A,X,Y,SP` |
| 7 | PC UPDATE | `PC_F`, `LEN`, `PC_MODE`, `Bus_Addr`, `TAKE` | `PC` |
| 8 | MEM WRITE | `WR_MEM`, адрес, данные | `Mem[]` |
| 9 | I/O BRIDGE | `Bus_Addr` в `$F000–$F0FF` | `GVL_IO`, физические `%Q` |
| 10 | IRQ CHECK | `GVL_IO.Io_In`, маска | `Latch`, `Irq` |
| 11 | BATCH COUNTER | счётчик | выбор следующей копии |

**Почему snapshot на стадии 0:** граф зависимостей становится ациклическим, и результат
**не зависит от порядка блоков**. Порядок исполнения всё равно выставляется явно
(`executionOrderId` обязателен для импорта), но корректность на нём не держится.

**Про `R_TRIG`:** в датапасе ядра триггеры **запрещены** — такт уже дискретизован сканом,
фронтовый детектор даст пропуск или двойное исполнение. `R_TRIG` ставится **только** в
`FB_IRQController`, то есть на границе с физическим миром, где фронт — реальное событие.

## 7. ПОРЯДОК РАБОТЫ

**Шаг 0 (дёшево, снимает главный риск).** Пробник синтаксиса вызова экземпляра FB: три
варианта записи → какой примет CODESYS. От результата зависит §4.

**Шаг 1.** Ядро 6502 на **одном листе** (архитектура уже подтверждена: POU на 2039
элементов / 526 блоков импортируется и компилируется). Выборка + дешифратор + адресация +
ALU + флаги + стек + запись + PC.

**Шаг 2.** `FB_IOBridge`, `FB_IRQController`, `FB_AnalogBridge`, карта `$F000–$F0FF`,
`ST_PhysicalIO` и маппинг `%IX/%QX/%IW/%QW`.

**Шаг 3.** `FB_DiskImage` (массив 256 КБ; файл на SD через `SysFile` — позже).

**Шаг 4.** `FB_BIOS_6502`: cold/warm boot, консоль, секторы, jump table `$FF00`,
векторы `$FFFC/FFFE`.

**Шаг 5.** Тесты: `TEST_6502` (команды) и `TEST_CPM_IO` (холодный старт, `A>`, загрузка
`.COM`, BDOS-вызовы, DIR, warm boot, DI→DO, AI/AO, IRQ).

**Шаг 6.** Витаминная программа «кибер-физика»: читает DI0 → включает DO0 / мигает DO1.

**Шаг 7.** HMI: регистры, дампер памяти, консоль 80×25, индикаторы DI/DO, кнопки
Cold/Warm boot, загрузка `.COM`, Reset IRQ.
