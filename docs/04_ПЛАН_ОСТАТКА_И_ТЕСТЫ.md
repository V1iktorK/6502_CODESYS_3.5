# 1. БЛОКЕРЫ И СПОСОБЫ ИХ СНЯТИЯ

## B1. `FB_IRQController` роняет процесс CODESYS при импорте

**Симптом:** процесс падает на импорте, POU не создаётся, исключения нет.
Схема статически чиста (0 замечаний), 35 блоков.

**Почему так, а не иначе:** это второй случай такого поведения (`FB_AddrGen` был
первым). Отличается от «молчаливого отказа»: там процесс жив, здесь — гибнет.

**План снятия — по возрастанию инвазивности:**

| Шаг | Действие | Критерий успеха |
|---|---|---|
| B1.1 | Импортировать `FB_IRQController` **в чистый проект отдельным прогоном** (один POU, без соседей) | POU создан → причина во взаимодействии, не в схеме |
| B1.2 | Бисекция по секциям: (а) только детектор фронта `XOR/AND`; (б) только маска; (в) только латч+`Irq` | находим минимальный падающий фрагмент |
| B1.3 | Если падает целое — **встроить логику IRQ прямо в главный лист** (`PRG_6502_CORE`), как сделано с ядром | IRQ работает без отдельного POU |

**Почему сначала B1.1:** дёшево и сразу отделяет «схема плохая» от «сессия плохая».

## B2. `FB_CPU_Core` отвергается при импорте

**Симптом:** 233 блока, статически чисто, но POU не создаётся (без исключения).

**Что уже исключено семью бисекциями:** запись в GVL, чтение+запись GVL,
много выходов экземпляра, `Mem[локальная]`, `Mem[GVL]`, необъявленные имена,
дубли объявлений, размер (233 блока против 524 у успешно импортированного
декодера), порядок импорта, состояние сессии, ссылка без префикса GVL.

**Осталась ОДНА непроверенная комбинация:** `FB_CPU_Core` — единственная схема
проекта, которая **одновременно вызывает экземпляр FB (`FB_Decoder6502`) и функции
(`F_UnpackByte`, `F_PackByte`)**. В `FB_FlagsReg` были только функции, в пробнике
`C_MANY_OUTS` — только экземпляр.

| Шаг | Действие | Критерий успеха |
|---|---|---|
| B2.1 | Пробник: POU, вызывающий **и экземпляр, и функцию** | создан → комбинация безопасна, причина иная |
| B2.2 | Если подтвердилось — **убрать вызовы функций**: распаковку битов `P` встроить 8×(`AND`+`NE`), упаковку — 8×`SEL`+OR-дерево | остаётся только экземпляр декодера |
| B2.3 | Если и это не поможет — **встроить декодер** в главный лист (инлайн) | работает: 2039 элементов уже импортировались ранее |

## B3. Замена устройства недоступна через API — СНЯТО

Причина `C0046` устранена сборкой на шаблоне с установленным устройством
(`TemplatePlc210_01`). Этот блокер закрыт, возврата к нему не будет.

# 2. ПЛАН РАБОТ — что делаем

## Этап 1. Ядро 6502: `FB_CPU_Core` (снятие B2)

**Что делаем:** доводим ядро до импорта по B2.1→B2.3. Ядро уже написано:
выборка → дешифрация (85 опкодов) → 12 режимов адресации (включая `(ind,X)`,
`(ind),Y` и намеренное воспроизведение бага `JMP (ind)`) → чтение → ALU с
байтовым переносом → флаги `P` с принудительным `bit5=1` → запись регистров →
стек с push3/pull3 (`BRK`/`RTI`) → три порта записи памяти → новый `PC` по семи
режимам → ветвление по шести условиям.

**Почему перенос на байтовом уровне** (`C1 := S1 < A`, `C2 := CINX AND S2 < S1`):
не нужны 16-разрядные суммы и преобразования типов, а логика переноса видна на
схеме глазами, как в реальном ALU.

**Проверка:** POU создан · `check_static.py` — 0 замечаний · в проекте
**0 ошибок компиляции**.

## Этап 2. Цепочка ядер и синхронизация: `PRG_6502_CORE`

**Что делаем:** главный лист с **N экземплярами `FB_CPU_Core`** (`Core0…CoreN-1`),
счётчик `CTU`, параметр `CPU_Insts_Per_Scan : UINT` (1…32). Счётчик зажигает
`Enable` экземпляров последовательно; состояние передаётся через `GVL_CPU`.

**Почему так:** ТЗ требует N инструкций за скан; при `N=1` — детерминированный
пошаговый режим для отладки. Синтаксис экземпляров FB подтверждён отдельным
опытом (CODESYS возвращает `<block typeName="..." instanceName="...">` как свою
каноническую форму).

**Проверка:** при `N=1` и `N=16` итоговое состояние идентично (тест T-SYNC-2) ·
0 ошибок компиляции.

## Этап 3. Монитор: `GVL_CONSOLE` + `FB_BIOS_6502`

CP/M-65 отсутствует (подтверждено заказчиком) — вместо BDOS+CCP пишем
**собственный минимальный монитор**. Это согласованное отступление от ТЗ.

**Что делаем:**
- `GVL_CONSOLE`: буфер 80×25 (`ARRAY[0..24] OF ARRAY[0..79] OF BYTE`), курсор, флаг вывода;
- `FB_BIOS_6502`: `BOOT` (PC := `Mem[$FFFC] | Mem[$FFFD]<<8`), `WBOOT`, `CONIN`, `CONOUT`,
  `READ`/`WRITE` сектора через `FB_DiskImage`, jump table `$FF00–$FF2F` (16 записей `JMP`),
  вектор IRQ `$FFFE/FFFF`.

**Почему little-endian именно здесь:** вектор reset собирается как
`LO OR (HI SHL 8)` — младший байт первым, как во всём 6502.

**Проверка:** после cold boot `PC` равен значению из `$FFFC/FFFD` · `JMP $FF00`
приводит в обработчик · символ из `CONOUT` попадает в буфер консоли.

## Этап 4. Тесты в FBD: `FB_AssertEq`, `TEST_6502`, `TEST_CPM_IO`

**Что делаем:** секвенсор `TEST_6502` — грузит кейс (программа в память, регистры,
`PC`) → снимает `CPU_Enable` → прогоняет `steps` сканов → сравнивает через
`FB_AssertEq` (`EQ` → `BOOL`) → пишет в `GVL_TEST.Pass[i]` → следующий кейс.

**Почему секвенсор, а не «все тесты сразу»:** один скан = одна инструкция,
поэтому кейс — это последовательность сканов; без секвенсора нельзя ни загрузить
состояние, ни дождаться нужного числа инструкций.

**Проверка:** `GVL_TEST.Done = TRUE`, счётчики `CTU` PASS/FAIL, таблица
«тест → ожидание → факт → PASS/FAIL».

## Этап 5. Прогон в симуляции (автоматический)

**Что делаем:** скрипт через `online.create_online_application` → `login`
(Simulation) → `start()` → `read_value("GVL_TEST.Pass[i]")` → отчёт в файл.

**Проверка:** все тесты PASS · **0 ошибок компиляции** · 0 FAIL.

## Этап 6. HMI

`VISU_CPU` (A/X/Y/P/SP/PC), `VISU_MEM` (дампер), `VISU_CONSOLE` (80×25),
`VISU_IO` (DI/DO/AI/AO/такты), кнопки Cold boot, Warm boot, Reset IRQ.
Привязка — только к GVL, схема не меняется.

## Этап 7. Оформление портфолио

Скриншоты схем, карта памяти, таблица опкодов, отчёт тестов, `README`.

# 3. ПЛАН ТЕСТИРОВАНИЯ — написан ДО кода

## 3.1. Принципы

1. **Ожидания — из документации 6502 и из ТЗ**, не из моей реализации.
2. **Стартовые `A/X/Y = $11/$22/$33` — все разные:** перепутанный провод даст FAIL,
   а не случайное совпадение.
3. **Каждый тест — последовательность сканов** (1 скан = 1 инструкция).
4. **Тест, который не может упасть, — не тест.** Для каждого указываю, что именно
   в схеме его сломает.
5. **Инвариант на каждом тесте:** `(P AND $20) = $20`.

## 3.2. Механика прогона

Секвенсор `TEST_6502` хранит индекс кейса (`CTU`), состояния «гружу / тикаю /
сравниваю». `GVL_TEST.Pass : ARRAY[0..N-1] OF BOOL`, `Done`, `Exp`, `Act`.
Для многотактовых сценариев кейс задаёт `steps`.

## 3.3. Тесты ядра (TEST_6502) — база 121 кейс + 4 новых

| Группа | Кейсов | Что ломает тест при ошибке |
|---|---:|---|
| `LDA/LDX/LDY` по всем режимам | 8+5+5 | неверный эффективный адрес, неверная длина инструкции |
| `STA/STX/STY` | 7+3+3 | запись не по тому адресу, «протечка» в соседнюю ячейку |
| Пересылки `TAX/TAY/TXA/TYA` | 6 | перепутаны регистры, не обновлён `N/Z` |
| `ADC/SBC/CMP` + границы | 14+14+12 | неверный перенос/заём, неверный `V` на границе знака |
| `INX/DEX/INY/DEY` | 8 | не обработан переход `$FF→$00` и `$00→$FF` |
| `CLC/SEC` | 3 | затёрты посторонние флаги |
| `JMP abs/ind` + баг страницы | 3 | перепутаны байты адреса, не воспроизведён баг `$xxFF` |
| `JSR/RTS` + стек | 3 | положен адрес возврата, а не «минус 1»; неверный `SP` |
| Ветвления `BEQ…BMI` | 13 | переход по чужому флагу, знаковое смещение |
| Стек `PHA/PLA/PHP/PLP` | 5 | push после декремента вместо «до»; `B=1` не выставлен |
| Little-endian | 2 | байты адреса переставлены |
| `NOP/HLT` | 3 | `PC` не заморожен при останове |
| Программы (цикл, подпрограмма, ZP+ADC) | 4 | сбой на многотактовых сценариях |

**Новые под ТЗ:**

| ID | Вход | Ожидание | Что ломает |
|---|---|---|---|
| T-BRK | `PC=$0250`, `SP=$FD`, `P=$24` | `Mem[$01FD]=$34` (P с `B=1`), `Mem[$01FC]=$02`, `Mem[$01FB]=$52`; `SP=$FA`; `PC` из `$FFFE/FFFF`; `I=1` | неверный порядок push, не выставлен `B`, не установлен `I` |
| T-RTI | `SP=$FA`, стек заполнен | `P` извлечён, `PC` извлечён **без +1**, `SP=$FD` | прибавлена единица, как у `RTS` |
| T-SEI | `I=0` | `I=1`, остальные флаги не тронуты | затёрты `N/Z/C/V` |
| T-CLI | `I=1` | `I=0` | то же |

# 4. ПРОЦЕДУРА ПРОГОНА

1. Сгенерировать схемы → `check_static.py` + `check_decl.py`.
2. Собрать: импорт 9→12 схем, GVL, сохранение **до** компиляции.
3. Компиляция → прочитать `get_messages(категория)`.
4. Если есть ошибки — **правка → полный повтор с шага 1** (регрессия обязательна:
   тесты ядра не должны деградировать при работе над I/O).
5. Прогон тестов через `online` API в симуляции.
6. Для каждого FAIL: причина (гонка на шине, задержка на такт, ошибка
   little-endian, логика стека, отсутствие ре-инициализации, неверный маппинг I/O)
   → правка → **прогон ВСЕХ тестов заново**.
7. Когда всё PASS — **прогнать тесты ещё раз** (проверка воспроизводимости).
8. Внести правки в этот план и в `docs\01_ПЛАН_ПРОЕКТА.md`.
9. Отчёт.
