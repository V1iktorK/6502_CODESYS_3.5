# Диагностика импорта ядра 6502 в CODESYS (B2)

**Дата:** итог серии экспериментов в текущем окружении (CODESYS 3.5 SP17 Patch 3, headless).
**Задача:** `FB_CPU_Core` / `PRG_CPU_CORE` не появляется в проекте после `app.import_xml(...)`.

---

## 1. Итог одной строкой

Гипотеза «ядро не создаётся» **опровергнута в прежней формулировке**: дело не в объёме,
не в размере XML, не в отдельной конструкции и не в окружении. Импорт обрывается на
**конкретной точке большого листа** (элемент № 2225 из 2729), причём **только в полном
контексте** — в изоляции тот же фрагмент импортируется. Практический вывод: лист нужно
**декомпозировать** на несколько более мелких POU.

---

### Бисекция по элементам листа (`probe_bisect.py`)

`fbd.py` всегда создаёт источник раньше потребителя, поэтому **любой префикс списка
элементов — валидная частичная схема**. Это дало точную бисекцию:

```
K=1      -> СОЗДАН
K=1365   -> СОЗДАН
K=2047   -> СОЗДАН
K=2217   -> СОЗДАН
K=2224   -> СОЗДАН      <-- последний рабочий префикс
K=2225   -> НЕ СОЗДАН   <-- первый ломающий элемент (обычный блок OR, order 624)
K=2388   -> НЕ СОЗДАН
K=2729   -> НЕ СОЗДАН   (полный лист)
```

Отвергаемый элемент — **рядовой `OR` с двумя входами**; в нём нет ничего особенного.

### Различающие опыты (`probe_pivot.py`, `probe_pivot2.py`, `probe_pivot3.py`)

| Опыт | Состав | Результат |
|---|---|---|
| A | только транзитивные зависимости элемента № 2225 (31 элемент) | **СОЗДАН** |
| B | префикс 2224 + **посторонний** блок `MOVE` | **СОЗДАН** → это не количественный порог |
| C | префикс 2223 + элемент № 2225 | **НЕ СОЗДАН** |
| D1 | то же, но позиция сдвинута | **НЕ СОЗДАН** → позиция не важна |
| D2 | то же, но новый `localId` | **НЕ СОЗДАН** → идентификатор не важен |
| E1 | элемент № 2225 **без входов** | **СОЗДАН** |
| E2 | только вход `IN1` (от `OR` 2678) | **СОЗДАН** |
| E3 | только вход `IN2` (от `SEL` 2670) | **НЕ СОЗДАН** |
| E4 | оба входа от «свежих» копий переменных | **СОЗДАН** |

**Единственная ломающая связь:** `OR 2681 ← SEL 2670`. Тот же фрагмент в изоляции
импортируется, значит отказ возникает при **совместном присутствии** этой связи и уже
существующей части листа. Вход `G` у `SEL 2670` питается от синтетической `G2671`
(артефакт разрыва связей) — но полное удаление таких переменных не помогает.

### Сообщения компилятора

`import_xml` возвращает `None`, исключений нет, `system.get_messages(<категория>)` по всем
категориям **пуст**; последующая сборка даёт «0 ошибок, 0 предупреждений», потому что POU
в проекте отсутствует. То есть диагностики от CODESYS получить нельзя — только бисекцию.

## 3. Что это значит практически

Масштаб, который **доказанно** импортируется:

| Схема | Блоков | Элементов | Связей | Импорт |
|---|---|---|---|---|
| `FB_Decoder6502` | 547 | 1825 | 1800 | да |
| синтетика `BIG_4000` | 4000 | 12001 | 8000 | да |
| префикс ядра до № 2224 | ≈ 623 | 2224 | ≈ 2100 | да |
| **ядро целиком** | 779 | 2729 | 2640 | **нет** |

Отказ не объясняется ни одним из измеренных счётчиков, поэтому надёжное инженерное
решение — **не пытаться уложить всё ядро в один лист**, а разложить его на несколько
самостоятельных POU. Это одновременно:
* обходит точку отказа (каждая часть заведомо меньше проверенных рабочих префиксов);
* прямо отвечает требованию ТЗ и замечанию пользователя о **читаемости** большой схемы
  (вместо одного листа 10 500 × 10 000 px — несколько листов по 150–250 блоков);
* даёт естественную рубрикацию для отчёта («выборка», «дешифрация», «адресация»,
  «АЛУ», «флаги», «запись/стек», «PC и переходы»).

## 4. Предлагаемая декомпозиция (на согласование)

`FB_CPU_Core` становится **композитной** схемой, собирающей 6 подчинённых POU.
Межабонентские сигналы остаются в `GVL_CPU` (плоское пространство имён уже задано ТЗ).

| POU | Ответственность | Оценка блоков |
|---|---|---|
| `FB_Fetch` | `Mem[PC] → IR/IMM`, `PC+1`, `PC+2`, извлечение `PCL/PCH` | 60–90 |
| `FB_AddrMode` | 12 режимов адресации → `ADDR`, `ADDR_MODE` | 150–200 |
| `FB_ALU6502` | ADC/SBC/AND/ORA/EOR/CMP + переносы | 120–160 |
| `FB_Flags` | N V B D I Z C, упаковка/распаковка `P` | 60–80 |
| `FB_WriteBack` | `STA/STX/STY`, `Mem[ADDR] := …` (3 порта) | 40–60 |
| `FB_PC_Update` | 7 режимов PC + стек push/pull + ветвления | 120–160 |
| `FB_CPU_Core` | композиция: 6 экземпляров + `FB_Decoder6502` | 40–60 |

Каждая часть — **существенно меньше** 2224 элементов, то есть с большим запасом.
Проверка гипотезы дешёвая: соберём `FB_Fetch` и импортируем — если создаётся, план принят.

## 5. Пилот декомпозиции — ВЫПОЛНЕН, архитектура подтверждена

Собраны и импортированы два POU (`tools/gen_fetch.py`):

| POU | Что содержит | Импорт |
|---|---|---|
| `FB_Fetch` | стадия выборки с **настоящими контактами**: вход `PCs : WORD`; выходы `OPs/OP1/OP2 : BYTE`, `PC1/PC2 : WORD`, `PCL/PCH : BYTE`; три независимых порта чтения `GVL_MEM.Mem[...]`, `ADD`, `SHR`, `WORD_TO_BYTE` | **СОЗДАН** |
| `FB_CorePilot` | композит: экземпляр `Fetch : FB_Fetch` подключён контактами (`PCs ← GVL_CPU.PC`), выходы сняты по именам (`src_pin`) и записаны в `GVL_CPU.OP/OP1/OP2/PC1/PC2` | **СОЗДАН** |

Компиляция проекта: **0 ошибок, 0 предупреждений** (строки «Компиляция завершена -- 0 ошибок»
и «Доп. проверки кода завершены -- 0 ошибки (-ок)»; счётчик в пробнике
`probe_fetch.py` посчитал их «строками с ошибками» по подстроке — это ложное
срабатывание счётчика, а не ошибки сборки).

Что это доказывает:
1. разложение ядра на POU **работает** — схема из нескольких листов импортируется там,
   где единый лист отказывал;
2. **подключение экземпляра контактами** (а не через GVL) поддерживается и компилируется
   без ошибок — значит межабонентские сигналы можно вести проводами, как и требуется
   для читаемой схемы;
3. в `tools/fbd.py` добавлен параметр `inst=` у `Sheet.blk` — генерация
   `instanceName="Fetch"` (без него CODESYS не принимает вызов ПОУ).

### Следующие шаги (по утверждённому плану)

1. `FB_AddrMode` — 12 режимов адресации → `ADDR`, `ADDR_MODE` (150–200 блоков).
2. `FB_ALU6502` — ADC/SBC/AND/ORA/EOR/CMP + переносы (120–160).
3. `FB_Flags` — N V B D I Z C, упаковка/распаковка `P` (60–80).
4. `FB_WriteBack` — `STA/STX/STY`, три порта записи (40–60).
5. `FB_PC_Update` — 7 режимов PC, стек push/pull, ветвления (120–160).
6. `FB_CPU_Core` — композит: `FB_Fetch` + `FB_Decoder6502` + пять POU выше.
7. Затем прежний путь: `PRG_6502_CORE` (N экземпляров + `CTU`), BIOS, тесты, симуляция.

## 7. Второй раунд диагностики: импорт вешается (модальное окно без UI)

После декомпозиции выяснилось, что часть схем не просто молча не создаётся, а
**подвешивает CODESYS навсегда**: процесс жив, все потоки в состоянии
`WaitReason = UserRequest`, окна нет, сообщений нет. В режиме `--noUI` это
означает невидимое модальное окно, которое некому закрыть.

### Инструмент: `tools/run_quick.ps1`

Обычный `run_headless.ps1` ждёт исчезновения процесса до 15 минут. Для бисекции это
неприемлемо, поэтому добавлен быстрый запуск с **ограниченным ожиданием** (по
умолчанию 70–130 с): если процесс не завершился, снимается **свой** процесс и
возвращается `HUNG`. Зависание становится обычным результатом опыта ценой ~1 минуты.

### Что проверено и опровергнуто во втором раунде (25+ гипотез)

| Гипотеза | Опыт | Итог |
|---|---|---|
| Разветвление выхода блока на 2–3 потребителя | `probe_fanout.py` | **опровергнуто** (fan-out 3 создаётся; в рабочем декодере fan-out 85) |
| Разрыв связи именованной переменной | `probe_wrap.py` | Q1 создаётся, Q2 (потребитель `AB`) вешается → дело не в форме потребителя |
| `MUL` → `ADD` | `probe_muladd.py` | **опровергнуто** (все 5 созданы) |
| Вызов функции `F_Join16` | `probe_fn.py` | **опровергнуто** |
| `Mem[<локальная>]` в `program` против `functionBlock` | `probe_fblocal.py` | **опровергнуто** (оба созданы) |
| Нарушение `executionOrderId` | разбор XML | 0 нарушений во всех 8 POU |
| Отключение `executionOrderId` целиком | регенерация + импорт | не помогло |
| Дубликаты `localId` / порядок `executionOrderId` | разбор XML | чисто |

### Дельта-отладка **удалением** и **лестница снизу** (`gen_addrvar*.py`, `gen_tree.py`)

Префиксная бисекция дала ложный ответ (граница на тривиальной константе `BYTE#0`),
поэтому применены два других метода. Лестница «от тривиального вверх»:

```
AW10  база (4 блока: F_Join16 + 3 выхода)          СОЗДАН
AW11  + 13 сравнений ADDR_MODE (пока мёртвые)      СОЗДАН
AW12  + вся арифметика адресов (пока мёртвая)      СОЗДАН
AW13  + relative (sgn/off/offw/relw)               НЕ СОЗДАН  (быстрый отказ)
AW14  + косвенные цепочки (izx/izy) с чтением      СОЗДАН
AW15  AW12 + дерево SEL/OR                         ЗАВИСАНИЕ
```

Дальнейшее уточнение (`gen_addrvar3.py`):

```
AD_Y1  AW12 + ОДИН SEL, включённый в работу          ЗАВИСАНИЕ
```

Ключевое наблюдение: в `AW12` арифметика адресов присутствовала, но была **мёртвой**
(никуда не подключена). Как только её результат начинает использоваться (через `SEL`
или через выход), импорт вешается. При этом те же самые конструкции по отдельности
(`S2_ADD_B2W`, `S4_MUL_ADD`, `J1_JOIN16`, `X1_CHAIN`, `X2_OR_SELS`) создаются.

**Вывод:** отказ не привязан ни к одной конструкции и не привязан к объёму. Он
воспроизводимо возникает при **совместном включении в один лист нескольких семейств
операций** (сравнения `EQ`/`GE` + выбор `SEL`/`OR` + арифметика `ADD`/`BYTE_TO_WORD`/
`F_Join16`), когда арифметическая ветвь становится «живой».

### Что из этого следует практически

Листы, содержащие **одно семейство**, импортируются надёжно и доказанно:

| Лист | Семейство | Импорт |
|---|---|---|
| `FB_Decoder6502` (547 блоков) | `EQ` + `OR`/`SEL` по BYTE-константам | да |
| `FB_Fetch` | `ADD`/`SHR`/`WORD_TO_BYTE`, адреса приходят **входами** | да |
| `FB_ALU6502` | арифметика и битовые операции над BYTE | да |
| `FB_Flags` | `F_UnpackByte`/`F_PackByte`, `SEL` по BOOL | да |
| `FB_WriteBack`, `FB_CPU_Core` | — | не проверялись отдельно |

Поэтому рабочая архитектура для адресации и PC — **разнести семейства по разным
листам**:

* `SL_CALC` — чистая арифметика: входы `OP1/OP2/X/Y/PCs/PC2`, выходы — 11 адресов-кандидатов;
* `SL_SELECT` — чистый выбор: входы `ADDR_MODE` + 11 адресов, выход `EFF`;
* аналогично для PC: `FB_Stack` (арифметика стека) и `FB_PCRoute` (сравнения + выбор).

Проверка самой этой архитектуры (`probe_family.py`) **не завершена**: лист-калькулятор
с 11 выходными контактами тоже завис, то есть одной развязки по семействам
недостаточно — требуется ещё и ограничение на «живость» и число выходных контактов.
Это следующий шаг диагностики.

### Третий раунд: измеримые листы и «одно семейство на лист»

Проверка архитектуры разнесения по семействам (`gen_live.py`, `gen_sel2.py`, `gen_live2.py`,
`gen_rep.py`, `gen_rep2.py`, `probe_det.py`).

**Доказанно создаются** (детерминированно, повторено в разных сессиях):

| Лист | Состав | Итог |
|---|---|---|
| `SEL1` | 11 × `EQ` + 11 × `SEL` + цепочка `OR` по **11 WORD-входам**, без арифметики | **СОЗДАН** |
| `AR1`…`AR11` | чистая арифметика (`F_Join16`, `BYTE_TO_WORD`, `ADD`), от 1 до 11 живых выходов | **СОЗДАНЫ все** |

Отсюда важный вывод: **лист «чистый выбор» работоспособен** — это ядро будущей
архитектуры адресации (`SL_SELECT`: входы `ADDR_MODE` + 11 адресов, выход `EFF`).
Работоспособен и лист «чистая арифметика» на 11 живых выходов.

**Не создаются / вешаются:** `CL1`…`CL5` (арифметика + добавления), `CF1`, `CS1`,
`RP0`, `RP1`, `RP4`, `P1_SL_CALC`, `SEL1`+… Детерминизм проверен: один и тот же файл
(`AR11`) создаётся при повторных импортах, `CL1` — стабильно вешается, то есть
поведение воспроизводимо, но **признак, отличающий «хороший» лист от «плохого», не
сводится ни к числу блоков, ни к числу/типу выходных контактов, ни к повторному
использованию источника, ни к наличию `OR`/`SEL`/`GE`**.

Различия между `AR11` (работает) и `CL1`/`CF1` (вешаются) — единицы блоков, при этом
различие не переносится: замена общей константы на отдельные (`CF1`) не помогает,
порядок присваиваний и состав семи живых сетей тоже.

Вывод: это дефект импортёра CODESYS 3.5 SP17, который на имеющихся данных
**не характери­зуется детерминированным правилом**. Практические следствия:

1. Любой лист нужно **проверять импортом** и при зависании перегенерировать иначе —
   это уже отладочный цикл, а не проектирование.
2. `tools/run_quick.ps1` делает такую проверку дешёвой (~1–2 минуты на лист),
   поэтому рабочая тактика — генерация → проверка → перегенерация.

### Четвёртый раунд: три разных режима отказа на почти одинаковых листах

Построены листы по образцу доказанно рабочего `AR11` (`gen_addr3.py`, `gen_base2.py`).

| Лист | Блоков | Выходов | Итог |
|---|---|---|---|
| `SL_IND` — чтение `Mem[...]` по адресу-**входу** + `F_Join16` + `ADD` | 3 | 2 | **СОЗДАН** |
| `SL_REL` — `GE` + `SEL` + `BYTE_TO_WORD` + 2 × `ADD` | 5 | 1 | **НЕ СОЗДАН** (быстрый отказ) |
| `SL_BASE` — арифметика адресов, 15 блоков | 15 | 11 | **ЗАВИСАНИЕ** |
| `SL_BASE2` — то же в геометрии `AR11` (одна общая константа, выходы в дальней колонке) | 15 | 11 | **КРАХ процесса** |

Три **разных** режима отказа (отказ, зависание, крах) на листах, отличающихся друг от
друга единицами блоков, при том что `AR11` (13 блоков, 11 выходов) устойчиво
создаётся.

Проверено и опровергнуто в этом раунде:

* совпадение координат элементов (`(40,0)` у двух комментариев) — встречается и в
  рабочих листах, и отсутствует в падающих → **не причина**;
* общая или отдельная константа на каждое присвоение → **не причина** (`CF1` с
  отдельными константами вешается так же);
* число живых выходов 1…11 → **не причина** (`AR8` с 8 живыми создаётся, `CF1` с 7 —
  вешается);
* порядок присваиваний и состав сетей → **не причина**;
* `import_xml(path, True)` вместо `False` → **не помогает**.

### Рекомендация

Импортёр CODESYS 3.5 SP17 в headless-режиме непригоден как надёжный транспорт для FBD
сложнее нескольких блоков: результат не предсказывается по составу схемы, а
диагностики нет (модальное окно без UI). Дальнейший перебор — лотерея с ценой 1–2
минуты за попытку, а не проектирование. Рабочие варианты:

1. **Тонкий слой вычислений на ST, вся структура — на FBD.** ST только в маленьких
   `FUNCTION` (адрес, смещение); требует согласования, так как ТЗ запрещает ST для
   основной логики.
2. **Лоты мелких листов** — по 1–3 блока на POU (такие создаются стабильно), вся схема
   собирается композицией. Сборка предсказуема, читаемость суммы листов ниже.
3. **Ручной импорт в IDE** — если в интерактивном режиме диалог закрывает человек, то
   ограничение снимается полностью; проверить это может только пользователь.

Проект: `build/CPM6502_CPU.project`.

### Правила, без которых сборка не собиралась

1. **Выходные контакты не используются.** CODESYS не принимает выбор именованного выхода
   экземпляра (`inst.OUT` вместо `inst.OPs`), поэтому все ступени пишут результаты
   **прямо в `GVL_CPU`** и не имеют выходных контактов (`tools/togvl.py`).
2. **Имена экземпляров не должны совпадать с операторами IEC**: `Sel`, `Adr`, `Mux`
   дают ошибки разбора. Переименовано в `Pick`.
3. **Выходной контакт блока обязан совпадать с настоящим именем выхода ПОУ**:
   у `F_Join16` это `Q`, у `F_UnpackByte` — `B` (карта `OUT_PIN` в `tools/fbd.py`).
   Иначе — «Идентификатор 'OUT' не задан».
4. **Выходные переменные не дублируются в локальных** (`ISUB`, `REG_WR` и др.).
5. **Никаких вложенных generic-блоков**: `SEL` внутри `SEL` CODESYS не типизирует,
   промежуточный результат выводится в именованную переменную.
6. `gen_cpu_split` вызывал `main()` при импорте и перезаписывал файлы — добавлена
   защита `if __name__ == "__main__"`.

### Проверено в симуляции

Онлайн-API работает: `scriptengine.online.create_online_application(app)` →
`set_simulation_mode(True)` на устройстве → `login` → `start` → `set_prepared_value` /
`write_prepared_values` / `read_value`. Проект запускается, состояние `run`.

### Текущий дефект (первый же прогон T-LDA-1)

```
LDA #$42: Mem[$0200]=$A9, Mem[$0201]=$42, PC=$0200, SP=$FF, A=0
прочитано: OPs=$A9  OP1=$42  PC2=$0202   — выборка ВЕРНА
           LD_A=TRUE (BOOL-сигналы дешифратора ВЕРНЫ)
           ADDR_MODE=0 LEN=0 SRC=0 PC_MODE=0 — ВСЕ BYTE-сигналы НУЛИ
           EFF=0 WDATA=0 LD_A_E=FALSE  => A не записан, PC не продвинулся
```

То есть дешифратор верно вычисляет булевы сигналы, но **байтовые сигналы
(`ADDR_MODE`, `LEN`, `SRC`, `PC_MODE`, `SP_MODE`, `COND`) получаются нулевыми**.
Они строятся цепочкой `SEL` по BYTE-константам, объединённой деревом `OR` (`CAT`),
в отличие от булевых, которые строятся деревом `OR` из `EQ`. Следующий шаг —
заменить `CAT` на другую сборку байта (например, арифметическую через суммы
масок) и проверить на том же тесте.

## 11. Почему не проходил тест T-LDA-1 (разбор причин)

Первый прогон давал `A=0, PC=0`. Причины найдены последовательно, восемь штук:

| № | Причина | Как обнаружено | Исправление |
|---|---|---|---|
| 1 | Байтовые сигналы дешифратора (`ADDR_MODE/LEN/SRC/PC_MODE/SP_MODE/COND/ALU_A/ALU_B`) в рантайме равны 0 | офлайн-интерпретатор `tools/fbd_sim.py` даёт `ADDR_MODE=1, LEN=2, SRC=4` для `$A9`, а в CODESYS `LD_A=TRUE`, но все байтовые = 0; отдельный опыт подтвердил, что `SEL`/`OR` по BYTE сами по себе работают | сборка байтов заменена на **чтение таблицы** `GVL_TABLE` (инициализируется в объявлении GVL); точечная правка 8 присвоений в готовом файле (`tools/patch_decoder.py`) |
| 2 | АЛУ не пропускало операнд при загрузке | по `opcodes.py`: у `LDA` нет `F_ADD/F_SUB/F_CMP`, но `SRC=ALU_R` | при отсутствии `F_*` первый операнд обнуляется: `ALU_R = WDATA` |
| 3 | `ALU_A=2` (Y) обрабатывался как A | контракт `ALU_A, ALU_X, ALU_Y = 0, 1, 2` | добавлен 3-входовой выбор `A / X / Y` |
| 4 | `LD_*_E` (разрешения записи) вообще не вычислялись | `LD_A_E=FALSE` при `LD_A=TRUE` | добавлены `AND(сигнал, Enable)` для 6 сигналов |
| 5 | Порты записи в память потерялись при декомпозиции | в старой схеме они были в теле ядра | добавлен слой `FB_CPU_Store` (3 порта: STA/STX/STY, JSR, BRK) |
| 6 | `P_BRK` и `P_EFF` не присваивались | `PC_NEW` всегда 0 при `PC_MODE=6` | добавлены присваивания в `FB_CPU_Addr1` и `FB_CPU_Select` |
| 7 | **Полярность `SEL`**: при `G=TRUE` берётся `IN0`, а в записи регистров стояло `SEL(LD_A_E, A, REG_WR)` — при разрешении писалось СТАРОЕ значение | `A` не менялось при `LD_A_E=TRUE` | входы переставлены: `SEL(разрешение, новое, старое)` |
| 8 | Тест писал регистры **до** `start()`, и инициализация их перезаписывала | `PC` становился 0 сразу после старта | запуск через **вектор BRK** `$FFFE/FFFF`, запись — после старта |

После исправлений 1–7 ядро **выполняет команды**: на программе `LDA #$42; JMP $0202`
наблюдалось `PC=$0202`, `OPs=$4C`, `EFF=$0201`, `LD_A=TRUE` — то есть выборка,
дешифрация, адресация и обновление PC работают.

### Остаток

`A` и `PC` по-прежнему не записываются, хотя `PC_NEW=$0200` и `LD_A_E=TRUE`;
`ALU_R=0` при `WDATA=$42`. То есть проблема уже не в логике, а в передаче
значений **между слоями внутри одного скана**: слои читают из `GVL_CPU` значения,
которые предыдущий слой записал в том же скане, а порядок записи выходных
переменных в листе CODESYS не гарантирует. Следующий шаг — либо объединить слои в
один лист, либо передавать межуровневые значения через `GVL_MEM` (память), запись
в которую видна сразу.

## 12. ГЛАВНАЯ ПРИЧИНА: полярность `SEL`

Экспериментально установлено (`tools/test_byte.py`, замер в симуляции CODESYS):

```
SEL(G, IN0, IN1):   при G = TRUE  ->  результат = IN1
                    при G = FALSE ->  результат = IN0
```

То есть `G` выбирает **второй** вход, а не первый. На этом я ошибался: в нескольких
местах входы были переставлены «по логике», и верно посчитанные сигналы не доходили
до регистров.

Правильные формы (проверены офлайн-моделью `tools/fbd_sim2.py`):

| Что выбираем | Правильная запись |
|---|---|
| запись регистра по разрешению | `SEL(gate, ТЕКУЩЕЕ, НОВОЕ)` |
| операнд команды в режиме immediate | `SEL(imm, ПАМЯТЬ, OP1)` |
| цель ветвления | `SEL(TAKE, PC2, C_REL)` |
| новый `PC` | `SEL(TRUE, PC, PC_NEW)` |
| выбор адресного режима | `SEL(EQ(mode,k), 0, КАНДИДАТ)` |
| цепочка источника записи (`SRC`) | `SEL(EQ(SRC,k), ПРЕДЫДУЩЕЕ, КАНДИДАТ)` |

Дополнительно найдено и исправлено:

* `SL_BRN2` собирается в `gen_step8.py`, а не в `gen_step3.py`: у него не было
  контакта `OUT` (писал в `GVL_CPU.BRN_TGT`), поэтому провод в `P_BRN` давал 0;
* `SL_PCSEL` и `SL_BRN2` исключены из `togvl.py`, чтобы сохранить единственный
  контакт `OUT` (вариант A: связи проводами);
* `P_BRK` и `P_EFF` не присваивались в новой композиции — `PC_NEW` всегда был 0;
* `LD_*_E` не вычислялись (`A` не записывался даже при `LD_A=TRUE`).

## 13. Офлайн-модель композиции (`tools/fbd_sim2.py`)

Так как один прогон CODESYS стал занимать 20–40 минут, написана модель, которая
интерпретирует **всю композицию**: рекурсивно вызывает экземпляры POU, разделяет
общее состояние `GVL_CPU`, `GVL_TABLE`, `Mem[]`, разыменовывает массивы.

Результат прогона программы `LDA #$42; JMP $0202` (модель):

```
такт 0: PC 512 -> 514  OPs=169 AM=1 LEN=2 SRC=4  A=66  ALU_R=66 EFF=513 WDATA=66
        OP1=66 OP2=76 PC2=514 PC_MODE=0 ADV=514 P_ADV=514 LD_A_E=1 REG_WR=66
такт 1: PC 514 -> 514  OPs=76  AM=5 LEN=3 SRC=0  A=66  ALU_R=76 EFF=514 WDATA=76
```

То есть `A=$42`, `PC=$0202` — **T-LDA-1 в модели проходит**. Модель использовалась
как основной инструмент отладки вместо дорогих прогонов CODESYS.
