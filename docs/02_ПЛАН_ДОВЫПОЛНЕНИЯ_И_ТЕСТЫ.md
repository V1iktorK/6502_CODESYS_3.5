# ЧАСТЬ 0. БЛОКЕР: ошибка C0046

`C0046: Идентификатор 'IoConfigTaskMap' не задан` в `Application [PLCWinNT: Plc Logic]`.

**Это не ошибка логики и не моих схем.** Она присутствовала с самого первого
скриншота, до всех изменений. Источник — устройство `PLCWinNT (CoDeSys SP Win V3)`
из шаблона `Templates\Standard.project`: у него есть конфигурация ввода-вывода,
не привязанная к задаче, и компилятор не находит идентификатор `IoConfigTaskMap`.

**Почему я не могу исправить это сам:** метода `add_device` в Scripting API **нет**
(проверено по полному дампу API), а у объекта устройства нет методов замены.
Устройство меняется только в IDE.

**Три пути, по надёжности:**

| Путь | Действия | Надёжность |
|---|---|---|
| **A. Сменить устройство** | правый клик по `PLCWinNT` → «Изменить устройство…» → `CODESYS Control Win V3` → ОК → `F11` | высокая |
| **B. Обновить устройство** | правый клик по `PLCWinNT` → «Обновить устройство…» → `F11` | средняя |
| **C. Чистый проект** | Создать новый проект в IDE с устройством `CODESYS Control Win V3`, затем в него импортировать 6 файлов из `plcopen\` (`F_UnpackByte`, `F_PackByte`, `F_Join16`, `F_Split16`, `F_Add16`, `FB_Decoder6502`) через «Проект → Импорт PLCopen XML» | **гарантированная** |

Путь C надёжнее всех: он не зависит от того, что за устройство в шаблоне.
Схемы уже готовы и проверены статически — импорт занимает минуту.

# ЧАСТЬ 1. ПЛАН ДОВЫПОЛНЕНИЯ ТЗ

## Этап 1. Шины и карта памяти (ТЗ п. «Шины»)

**Что создать:** `GVL_BUS` — `Bus_Data : BYTE`, `Bus_Addr : WORD`, `Bus_WE`, `Bus_RE : BOOL`.
**Что ещё:** `GVL_MAP` — `VAR CONSTANT`: `ZP_START=$0000`, `STACK_PAGE=$0100`,
`TPA_START=$0200`, `IO_WIN=$F000`, `IO_WIN_END=$F0FF`, `BIOS_VEC=$FF00`,
`RESET_VEC=$FFFC`, `IRQ_VEC=$FFFE`.

**Почему так:** шина в GVL — требование ТЗ; константы карты в отдельной GVL,
чтобы HMI и отладка читали адреса, а не хардкодили их в схемах.

**Проверка:** `check_decl.py` — имена `Bus_Data`, `Bus_Addr` объявлены в GVL_BUS,
схемы ссылаются на них через `GVL_BUS.Bus_Data`.

## Этап 2. Окончание ядра: `FB_CPU_Core`

**Состояние:** схема написана (233 блока, статически чистая — 0 замечаний),
но CODESYS её не создаёт. Проведено 7 бисекций, исключены: запись в GVL,
чтение+запись GVL, много выходов экземпляра, `Mem[локальная]`, `Mem[GVL]`,
необъявленные имена, дубли, размер, порядок импорта, состояние сессии.

**Осталась ОДНА непроверенная комбинация:** `FB_CPU_Core` — единственная схема
проекта, которая одновременно **вызывает экземпляр FB (`FB_Decoder6502`) и функции
(`F_UnpackByte`, `F_PackByte`)**. В прошлом проекте `FB_FlagsReg` вызывал функции
без экземпляра, пробник `C_MANY_OUTS` вызывал экземпляр без функций.

**План:** пробник, вызывающий И экземпляр, И функцию. Если гипотеза верна —
разнести: распаковку битов `P` встроить прямо в схему (8×`AND`+`NE`), тогда
останется только экземпляр декодера.

**Проверка:** `FB_CPU_Core` создаётся в проекте, `check_static.py` — 0 замечаний.

## Этап 3. Цепочка ядер и синхронизация (ТЗ п. «Синхронизация»)

**Что построить:** `PRG_6502_CORE` — главный лист с N экземплярами `FB_CPU_Core`
(`Core0…CoreN-1`), `CTU` в роли счётчика, `CPU_Insts_Per_Scan : UINT` (1…32).

**Как замыкается:** каждый экземпляр имеет вход `Enable`; счётчик зажигает
их последовательно за один скан; состояние передаётся через `GVL_CPU`
(общая память состояния), поэтому цепочка не требует протяжки проводов.

**Почему так:** ТЗ требует N инструкций за скан, при `N=1` — детерминированный
пошаговый режим для отладки. Синтаксис экземпляров FB подтверждён (Шаг 0).

**Проверка:** `N=1` и `N=16` дают идентичное итоговое состояние при разном числе
сканов — это тест синхронизации (см. Часть 2, тест T-SYNC).

## Этап 4. Мост I/O и окно $F000–$F0FF (ТЗ п. «Подсистема I/O»)

**Карта окна (точно по ТЗ):**

| Адрес | Содержимое | Тип |
|---|---|---|
| `$F000` | дискретные входы DI0…DI7 (битовая карта) | BYTE |
| `$F001` | дискретные выходы DO0…DO7 (чтение — состояние, запись — управление) | BYTE |
| `$F002–$F003` | AI0, little-endian | WORD |
| `$F004–$F005` | AO0, little-endian | WORD |
| `$F006` | маска разрешения IRQ по DI | BYTE |
| `$F007` | флаг фронта (edge latch), сбрасывается чтением | BYTE |
| `$F008` | счётчик тактов PLC | BYTE |

**Что создать:** `GVL_IO` (`Io_In`, `Io_Out : BYTE`; `Ai0`, `Ao0 : WORD`;
`IrqMask`, `Latch`, `Tick : BYTE`), `FB_IOBridge` (FBD), `FB_IRQController` (FBD),
`FB_AnalogBridge` (FBD), `ST_PhysicalIO`.

**`R_TRIG` — только здесь:** детектор фронта физического DI, потому что фронт —
реальное событие внешнего мира. В датапасе ядра триггеры запрещены (такт уже
дискретизован сканом).

**`RS` — только для edge latch** в `$F007`.

**Проверка:** запись байта в эмулируемую `$F001` меняет `GVL_IO.Io_Out`;
чтение `$F000` возвращает `GVL_IO.Io_In`; фронт DI при установленной маске
поднимает `Latch` и `Irq`.

## Этап 5. Образ диска (ТЗ п. «Подсистема CP/M»)

**Что создать:** `FB_DiskImage` — `Disk : ARRAY[0..2047, 0..127] OF BYTE`
(2048 секторов × 128 байт = 256 КБ, формат 8″).
Порты: `Track`, `Sector : BYTE`; `WE : BOOL`; `WD : BYTE` → `RD : BYTE`.

**Почему так:** 128-байтные сектора и 32-байтные directory entries — формат
CP/M 2.2, как в ТЗ. Чтение/запись файла `DISK.IMG` на SD — через `SysFile`,
это единственное место со ST (файловый I/O, не логика).

**Проверка:** запись байта в сектор и чтение его обратно даёт то же значение;
номер сектора пересчитывается в индекс `[track*32 + sector]`.

## Этап 6. Монитор вместо CP/M-65 (ТЗ п. «Подсистема CP/M»)

**Важно:** исходников и бинарника CP/M-65 у заказчика **нет** (подтверждено).
Поэтому вместо готового BDOS+CCP пишется **собственный минимальный монитор** —
это отступление от буквы ТЗ, зафиксированное и согласованное.

**Что создать — `FB_BIOS_6502` (FBD):**
- cold boot: `PC := Mem[$FFFC] | Mem[$FFFD]<<8` (little-endian, младший байт первый);
- warm boot: возврат в монитор;
- `CONIN` / `CONOUT` — консоль через `GVL_CONSOLE` (буфер 80×25);
- `READ` / `WRITE` сектора через `FB_DiskImage`;
- jump table `$FF00–$FF2F`: 16 записей вида `JMP handler` (3 байта каждая);
- вектор IRQ `$FFFE/FFFF` → обработчик.

**Проверка:** после cold boot `PC` равен значению из `$FFFC/FFFD`;
`JMP $FF00` приводит в обработчик; вывод символа в `CONOUT` попадает в буфер консоли.

## Этап 7. Тесты и HMI

`TEST_6502` (команды ядра), `TEST_CPM_IO` (интеграция), `FB_AssertEq`.
HMI: `VISU_CPU` (A/X/Y/P/SP/PC), `VISU_MEM` (дампер), `VISU_CONSOLE` (80×25),
`VISU_IO` (DI/DO, AI/AO, счётчик тактов), кнопки Cold/Warm boot, Reset IRQ.

# ЧАСТЬ 2. ПЛАН ТЕСТИРОВАНИЯ (написан ДО кода)

## 2.1. Принципы

1. **Ожидания берутся из документации 6502 и из ТЗ**, а не из моей же реализации.
2. **Стартовые A/X/Y = $11/$22/$33 — все разные**: перепутанные провода дадут FAIL,
   а не случайное совпадение.
3. **Каждый тест — последовательность сканов** (1 скан = 1 инструкция).
4. **Инвариант на каждом тесте:** `(P AND $20) = $20` (bit5 всегда 1).
5. **Тест, который не может упасть, — не тест.** Для каждого проверяю: какое
   именно изменение в схеме его сломает.

## 2.2. Тесты ядра 6502 (TEST_6502)

База — 121 кейс из `tools\testcases.py` (уже написаны). Группы:

| Группа | Кейсов | Что проверяет |
|---|---:|---|
| LDA / LDX / LDY по всем режимам | 8+5+5 | загрузка, N/Z, длина инструкции, эффективный адрес |
| STA / STX / STY | 7+3+3 | запись ровно в одну ячейку, P не меняется |
| Пересылки TAX/TAY/TXA/TYA | 6 | N/Z, значения |
| ADC / SBC / CMP + границы | 14+14+12 | перенос, заём, V, Z, N на границах |
| INX/DEX/INY/DEY | 8 | N/Z, переход через $FF и $00 |
| CLC/SEC | 3 | только флаг C |
| JMP abs / ind / баг страницы | 3 | little-endian, воспроизведение бага `$xxFF` |
| JSR / RTS / стек | 3 | адрес возврата−1, SP, порядок байт |
| Ветвления BEQ…BMI | 13 | переход выполнен / не выполнен, знаковое смещение |
| Стек PHA/PLA/PHP/PLP | 5 | push до декремента, pull после инкремента |
| Little-endian | 2 | `$0342` читается, `$4203` не путается |
| NOP / HLT | 3 | PC, останов |
| Программы (цикл, подпрограмма, ZP+ADC) | 4 | многотактовые сценарии |
